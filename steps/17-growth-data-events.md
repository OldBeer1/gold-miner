# 第 17 步：成长数据定义与规则事件

状态：待开始。目标版本：v1.2.0。前置：第 13～16 步已完成，当前 v1.1.0 游戏及检查入口可用。

## 1. 开始前读取

按项目接手顺序读取 [AGENTS.md](../AGENTS.md)、[README.md](../README.md)、[现行游戏规格](../GAME_SPEC.md)、[实施计划顶部与最新交接](../IMPLEMENTATION_PLAN.md)、[验收记录](../VALIDATION.md)。再读 [功能规划](../FEATURE_ROADMAP.md) 第 2～6、8、10～11 节及本文件。

检查 Git 工作区、`js/config.js`、`js/rules.js`、`js/game.js` 和已有纯规则检查。复用浏览器与 Node.js 共用的规则组织方式。

## 2. 本步完成后

规则层能够提供成长系统所需的准确事件和本关暂存数据，18 项成就与 9 类图鉴有稳定定义。当前采矿、奖励、商店及入口保存行为保持有效。本步暂不写永久档案，也不新增玩家资料页面。

## 3. 实现范围

1. 落实规划中的统计口径和稳定 ID：成就清单、8 类可回收物、9 类图鉴、钱袋 5 档和宝箱 3 档。
2. 记录成功出钩、每次出钩最多一次命中、成功回收、空钩结束、炸药销毁、桶爆炸、结算等事实。无效输入不计出钩，桶命中不计回收。
3. 为 `banked` 补齐实际判定所需信息：奖励基础档位、应用效果前后的剩余时间、实际增减量、回收前后收入与首次达标时刻。不要依靠动画文本或循环帧末状态反推事件时刻。
4. 保留 `exploded.destroyedIds` 的现有含义，在统计侧去重并排除触发桶。护符抵消、满炸药转换和延时上限分别记录基础结果与实际效果。
5. 建立本关暂存统计及条件状态：出钩、命中、回收、销毁、时长、连击、容器连胜、惩罚连续次数和成就候选所需事实。正式结算后暂存不可再次累加。
6. 以实际 `elapsedTime` 增量记录有效采矿时间；暂停、页面关闭和已经放弃的重试不计入最终提交时长。
7. 新关入口和恢复入口要明确区分；从同一入口重试时重建本关暂存，不把关内数据放进入口快照。

静态定义和玩家状态分开。若需要独立纯逻辑文件，沿用现有双环境导出模式，避免为了埋点引入框架或通用事件总线。定义阶段不得顺便调整成就阈值以外的玩法数值。

## 4. 验证与完成条件

| 检查 | 必须得到的结果 |
| --- | --- |
| 18 项成就与类型目录 | ID 唯一、条件可判定、收藏不要求回收火药桶 |
| 出钩、桶命中、炸药、在途超时 | 出钩／命中／回收分开，单钩不重复命中，销毁无回收收益 |
| 最后一秒入账与截止边界 | 捕获真实事件时刻；截止入账顺序沿用现有规则 |
| 上限、护符与剩 2 秒的古物 | 增量为实际结果；抵消为零，扣至零只损失 2 秒 |
| 一个长帧包含多个事件 | 每个事件顺序和前后值准确，不统一读取帧末时间 |
| 暂停与入口重试 | 暂停不增时长，重试本关暂存清零，种子与随机结果不变 |

对改动 JavaScript 执行语法检查，针对事件与暂存规则做有意义的检查，并运行 `scripts/check-rules.cjs`。规则检查应调用实际统计逻辑，不复制一份独立计数算法。浏览器流程有改动时补充相应交互验证。
