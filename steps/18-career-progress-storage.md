# 第 18 步：生涯统计与成长存档

状态：已完成（2026-10-04，本地验收）。目标版本：v1.2.0。前置：[第 17 步](17-growth-data-events.md) 已完成实际实现与验证。

## 1. 开始前读取

按项目接手顺序读取 [AGENTS.md](../AGENTS.md)、[README.md](../README.md)、[现行游戏规格](../GAME_SPEC.md)、[实施计划](../IMPLEMENTATION_PLAN.md) 和 [验收记录](../VALIDATION.md)。再读 [功能规划](../FEATURE_ROADMAP.md) 第 3、5、7～8、11 节、前置交接与本文件。

重点检查 `js/storage.js` 的版本校验、偏好序列化，`js/rules.js` 的快照，以及 `js/game.js` 的入关、恢复、成功、失败、交易、覆盖和返回流程。

## 2. 本步完成后

生涯数据和当前挑战可以一致保存、恢复及迁移。继续、重试、成功和失败不会重复累计。成就与图鉴状态容器已预留，完整页面和终局报告展示由后续步骤完成。

## 3. 实现范围

1. 按规划第 5 节建立生涯与单局累计，明确有效成绩、实际回收、失败关收入、时长、道具和分类型数据。
2. 建立稳定 `runId`、局开始纪录快照、提交关号和入口已计数标志。新挑战确认后才增加次数，取消不改变状态。
3. 落实统一提交设计：永久档案、当前入口／商店、单局累计和未来报告容器使用同一权威进度文档，或提供满足同等一致性的明确提交协议。
4. 新关入口只记录一次到达、发现和时间券；关内暂存只在正式成功或失败时提交，重试回滚。成功提交包含固定商店，恢复商店不再次结算。
5. 普通存储环境下失败提交清除活动挑战；返回主页保留入口；确认覆盖旧局标记主动放弃且只提交已有成果。为第 21 步提供同一提交中的最终报告接入点。
6. 使用显式适配器读取有效 v1.1.0 偏好和入口／商店；保留旧键、音效、最高成绩、最高通过关、布局、种子、资源、增益和报价。不能只替换版本字符串。
7. 迁入旧局标记统计不完整，旧总成绩用于该局成绩，不当作新版累计收入；旧最大通过关不是累计通过数或最高到达纪录。
8. 已有有效新文档时不回退读取旧挑战键；避免失败后旧存档重新成为可继续挑战。迁移重复尝试不重复导入。
9. 校验版本、已知 ID、金额、库存、计数、日期及状态关系；反馈读取、写入、删除和迁移的真实结果。存储失败保留可玩内存状态，提示关闭后可能恢复旧进度。
10. 为外部页面更新增加修订识别与暂停／重载提示。明确首发不支持多个页面并行写同一挑战，不能把修订号比较宣传成原子锁。

本步不得清除或伪造旧生涯数据，也不在读写失败时删除整个永久档案。未知新版本不得静默覆盖。若实现过程中必须改变规划中的权威存储方案，先写明一致性理由并同步规划，不额外引入运行依赖。

## 4. 验证与完成条件

| 检查 | 必须得到的结果 |
| --- | --- |
| 新挑战、取消覆盖、继续及入口重试 | 挑战 ID 与次数正确，本关重试数据回滚 |
| 成功、商店创建与连续恢复 | 收入、通过数、发现数和道具只提交一次，报价与限购固定 |
| 失败关 | 实际回收统计保留，有效成绩不增加，活动挑战结束 |
| 有效旧入口／旧商店迁移 | 资源和随机结果保留，统计标明不完整，历史键不改写 |
| 重复迁移与旧键残留 | 不重复累计，不复活已结束挑战 |
| 错误数据与存储拒绝 | 可玩性与真实提示兼容，无“已经保存／清除”的虚假成功 |
| 外部修订 | 识别变更并暂停或要求重载，不静默覆盖新的状态 |

扩展相关存储检查，执行 `scripts/check-checkpoints.cjs`、受影响规则检查与 JavaScript 语法检查。实际浏览器检查文件直开和本地服务的恢复、交易、迁移与错误提示，沿用现有脚本方式，受控条件单独注明。
